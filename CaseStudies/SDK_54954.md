# Case Study: dart-lang/sdk#54954 — Timeline Tracking from Native Code

# Issue Overview

Issue #54954 discusses exposing timeline tracing APIs through:

```cpp
dart_api_dl.h
```

so that native C/C++ code used inside Flutter applications can emit profiling events visible in:

* Perfetto,
* Flutter DevTools,
* Dart VM timeline tools.

The issue specifically references:

```cpp
Dart_RecordTimelineEvent
```

which is internally used by the Flutter engine for performance tracing.

The request is essentially:

```text
Allow native code to participate in Dart timeline profiling.
```

---

# Core Problem Identified

Currently:

* Dart timeline APIs are accessible from Dart code via:

```dart
import 'dart:developer';
```

* but native plugins/libraries using:

```cpp
dart_api_dl.h
```

cannot directly emit timeline events.

This creates an observability gap:

```text
Dart code is traceable,
native code is not.
```

For applications with:

* heavy C/C++ processing,
* background threads,
* native networking,
* graphics engines,
* real-time systems,

this becomes a major profiling limitation.

---

Timeline infrastructure

# Architectural Insights Learned

---

## 1. `dart:developer` Is Built on Lower-Level VM Timeline APIs

This issue reveals that:

```dart
Timeline.startSync()
```

eventually maps to:

```cpp
Dart_RecordTimelineEvent
```

inside the VM/runtime.

This is a major architectural insight.

It means:

```text
Timeline APIs are wrappers over lower-level VM tracing infrastructure.
```

This helps explain:

* why traces appear in Perfetto,
* how DevTools receives timeline data,
* how VM profiling is implemented internally.

---

## 2. Timeline Events Are VM-Level Features

The discussion mentions:

```text
development-only features
```

and states:

```text
timeline APIs are NOPs in release/product mode.
```

This is extremely important for my milestone because WebSocket profiling should:

* avoid affecting production performance,
* behave consistently with existing HTTP profiling,
* remain development/debug oriented.

This validates my proposal’s decision to reuse:

```dart
HttpClient.enableTimelineLogging
```

instead of introducing always-on instrumentation.

---

## 3. Timeline Recording Must Be Lightweight

The issue discusses:

* callback overhead,
* FFI thread synchronization,
* tracing overhead.

This highlights that:

```text
profiling instrumentation itself must remain cheap.
```

This is critical for WebSocket profiling because:

* frame events may occur extremely frequently,
* logging every message could become expensive,
* profiling overhead may distort performance measurements.

This directly connects to:

* `#48455` (timeline garbage generation),
* batching concerns in my proposal.

---

multi-threaded native tracing

* async execution,

* concurrent tracing.
