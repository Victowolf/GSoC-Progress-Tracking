# Case Study: dart-lang/sdk#39457 — WebSocket Connection Was Not Upgraded

# Issue Overview

Issue #39457 reports a:

```text
WebSocketException: Connection was not upgraded to websocket
```

error while attempting to connect to the Dart VM service using:

```dart
vm_service
```

The failure occurs during:

```dart
_WebSocketImpl.connect()
```

inside:

```dart
dart:_http/websocket_impl.dart
```

The application attempted to connect to:

```text
http://localhost:1234/ws#
```

but the server responded with a normal HTTP response instead of performing the required:

```text
HTTP → WebSocket protocol upgrade.
```

As a result, the WebSocket handshake failed.

---

# Core Problem Identified

WebSockets begin as normal HTTP requests.

To establish a WebSocket connection:

* the client sends an HTTP upgrade request,
* the server must respond with:

```text
101 Switching Protocols
```

If the server does not:

* support WebSockets,
* expose the correct `/ws` endpoint,
* or perform the upgrade correctly,

then:

```text
the connection fails before a WebSocket session is established.
```

That is exactly what happened in this issue.

---

# What Actually Happened Here

The user launched:

```bash
flutter run -d web
```

which starts a normal web development server.

Then the code attempted:

```dart
vmServiceConnect(host, port)
```

which internally tries to open:

```text
/ws
```

for VM service communication.

But the Flutter web server:

* was serving normal HTTP pages,
* not exposing the VM service websocket endpoint.

So:

```text
the server never upgraded the connection to WebSocket.
```

Result:

```text
WebSocketException
```

# Architectural Insights Learned

## 1. WebSocket Connections Start as HTTP

This issue reinforces an important protocol detail:

```text
WebSocket is initially an HTTP protocol upgrade.
```

This is important because:
my proposal extends existing:

```dart
HttpClient.enableTimelineLogging
```

infrastructure.

The issue validates that:

* HTTP and WebSocket tracing are closely related,
* WebSocket instrumentation naturally belongs near HTTP profiling infrastructure.

---

## 2. Connection Failures Are Important Profiling Events

This issue demonstrates that:

```text
failed WebSocket upgrades are meaningful runtime events.
```

A profiler should ideally capture:

* failed handshake attempts,
* invalid upgrade responses,
* connection rejection reasons,
* timing information.

This improves:

* debugging,
* DevTools observability,
* networking diagnostics.

---

## 3. `_WebSocketImpl.connect()` Is a Key Instrumentation Point

The stack trace clearly identifies:

```dart
_WebSocketImpl.connect()
```

as a critical lifecycle point.

This is highly useful for implementation planning because:
connection instrumentation likely belongs around:

* upgrade initiation,
* handshake completion,
* error propagation.

---

## 4. Error Paths Must Be Profiled Too

Profiling systems often focus only on:

```text
successful events.
```

This issue demonstrates that:

```text
failure paths are equally important.
```

Especially for:

* networking,
* sockets,
* async systems.

WebSocket profiling should therefore include:

* connection failures,
* protocol errors,
* abnormal closes,
* handshake exceptions.
