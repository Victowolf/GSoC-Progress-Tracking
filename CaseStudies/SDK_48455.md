# Case Study: dart-lang/sdk#48455 — Timeline Sync Events Generate Garbage

# Issue Overview

Issue #48455 reports that:

```dart
Timeline.startSync()
```

allocates objects every time it is called, generating unnecessary garbage and increasing GC pressure.

The issue points to:

```dart
sdk/lib/developer/timeline.dart
```

and suggests that Timeline event handling currently creates temporary objects that:

* increase allocations,
* trigger garbage collection,
* reduce profiling efficiency.

The proposed idea is to:

```text
reuse/recycle objects instead of allocating new ones repeatedly.
```

---

# Core Problem Identified

The issue identifies a fundamental profiling paradox:

```text
The profiler itself is generating performance overhead.
```

Every call to:

```dart
Timeline.startSync()
```

creates temporary allocations.

For low-frequency tracing this may be acceptable.

However, for:

* high-frequency events,
* real-time systems,
* networking,
* frame-level profiling,

the overhead becomes significant.

This means profiling instrumentation can:

* distort measurements,
* increase GC frequency,
* reduce runtime performance,
* affect responsiveness.

# Architectural Insights Learned

## 1. Timeline APIs Are Not Free

This issue reveals an extremely important insight:

```text
Timeline instrumentation itself has runtime cost.
```

Developers often assume profiling APIs are lightweight,
but this issue shows that:

* allocations occur,
* GC pressure increases,
* tracing overhead accumulates.

For high-frequency systems like WebSockets,
this overhead can become large enough to:

* affect timings,
* distort profiling results,
* degrade throughput.

---

## 2. Allocation Cost Matters More in Streaming Systems

HTTP profiling is usually:

```text
request-oriented
```

with relatively infrequent events.

WebSocket profiling is fundamentally different:

```text
stream-oriented and continuous.
```

A single WebSocket connection may:

* remain active for hours,
* emit thousands of frames,
* continuously generate events.

Therefore:

```text
small per-event overhead becomes multiplicative.
```

This issue is especially relevant because my proposal extends profiling from:

```text
discrete HTTP requests
```

to:

```text
continuous real-time streams.
```

---

## 3. Profiling Granularity Must Be Chosen Carefully

This issue demonstrates that:

```text
not every internal operation should become a timeline event.
```

Excessively granular instrumentation may:

* generate massive allocations,
* overwhelm timeline buffers,
* slow DevTools rendering,
* trigger frequent GC cycles.

This strongly affects WebSocket instrumentation design.

---

## 4. Object Recycling May Matter for Profiling Infrastructure

The issue proposes:

```text
recycling timeline objects using stacks/pools
```

This reveals that profiling infrastructure itself may require:

* allocation optimization,
* reusable buffers,
* object pooling,
* memory-efficient event handling.

This becomes increasingly important for:

* high-frequency networking traces,
* long-running socket sessions.
