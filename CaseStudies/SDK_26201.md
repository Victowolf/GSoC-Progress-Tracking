# Case Study: dart-lang/sdk#26201 — Async Equivalent for `Timeline.timeSync()`

## Issue Overview

Issue #26201 proposes adding an asynchronous equivalent to:

```dart
Timeline.timeSync()
```

The current API:

```dart
Timeline.timeSync()
```

is designed for synchronous operations and internally wraps execution with:

```dart
Timeline.startSync()
Timeline.finishSync()
```

However, modern Dart applications heavily rely on:

* Futures,
* Streams,
* asynchronous callbacks,
* event-driven systems.

The issue proposes an async-aware helper API similar to:

```dart
static Future<dynamic> timeAsync(
  String label,
  Future<dynamic> closure(), {
  Map<String, String> arguments
}) async {
  final TimelineTask pushTask = new TimelineTask();
  pushTask.start(label, arguments: arguments);
  try {
    return await closure();
  } finally {
    pushTask.finish();
  }
}
```

The proposal suggests using:

```dart
TimelineTask
```

instead of:

```dart
Timeline.startSync()
```

to correctly model async execution lifecycles.

---

# Core Problem Identified

The issue highlights a major limitation in the current Timeline API:

```text
Timeline.timeSync() cannot correctly represent asynchronous operations.
```

This creates problems because:

* async work spans multiple event-loop turns,
* execution may resume later,
* synchronous timeline scopes break across async boundaries.

As a result:

* traces may become fragmented,
* durations may become inaccurate,
* async operations become difficult to visualize properly.

# Architectural Insights Learned

---

## 1. Sync Timeline APIs Are Insufficient for Async Systems

This issue demonstrates that:

```dart
Timeline.startSync()
Timeline.finishSync()
```

are only appropriate for:

* immediate synchronous execution.

They are not suitable for:

* WebSocket streams,
* asynchronous frame handling,
* Future-based connection flows.

This is important because WebSocket communication is inherently event-driven and asynchronous.

---

## 2. Async Tracing Requires Lifecycle-Aware APIs

The issue proposes:

```dart
TimelineTask
```

because async operations:

* begin in one execution context,
* continue later,
* may finish on different callbacks.

This reveals that async tracing requires:

* persistent task identity,
* lifecycle continuity,
* explicit start/finish handling.

This is directly applicable to:

* long-lived WebSocket connections,
* streaming message flows,
* background socket listeners.

---

## 3. WebSocket Connections Behave Like Async Tasks

A WebSocket connection is not a single synchronous operation.

Instead, it resembles:

```text
an ongoing asynchronous task lifecycle
```

Example lifecycle:

```text
connect
↓
handshake
↓
message receive
↓
message send
↓
ping/pong
↓
close/error
```

This maps naturally to:

```dart
TimelineTask
```

rather than:

```dart
Timeline.timeSync()
```

---

## 4. Async Tracing Requires Proper Cleanup

The proposed implementation uses:

```dart
try/finally
```

This reveals an important profiling requirement:
timeline tasks must always finish correctly even during:

* exceptions,
* cancellations,
* disconnects,
* socket failures.

For WebSocket profiling this is especially important because:

* connections may terminate unexpectedly,
* streams may close abruptly,
* errors may interrupt event flows.
